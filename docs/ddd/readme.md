طراحی معماری مونولیتیک برای یک فروشگاه اینترنتی
برای این پروژه، یک فروشگاه اینترنتی در نظر می‌گیریم که مشتریان بتوانند حساب کاربری بسازند، وارد سایت شوند، محصولات را مشاهده کنند، سفارش ثبت کنند و پرداخت انجام دهند. مدیر فروشگاه نیز بتواند محصولات، موجودی و سفارش‌ها را مدیریت کند.

هدف این است که پروژه را با رویکرد Domain-Driven Design (DDD) تحلیل کنیم و سپس ساختار آن را در قالب یک معماری مونولیتیک (Monolithic Architecture) طراحی کنیم.

نکته مهم: مونولیتیک یعنی بخش‌های اصلی برنامه در قالب یک نرم‌افزار واحد توسعه و اجرا می‌شوند؛ نه اینکه تمام کدها را در یک فایل بنویسیم. هر بخش می‌تواند مسئولیت و ساختار داخلی مستقل خودش را داشته باشد.
مرحله ۱: تعریف Domain (دامنه)
Domain به حوزه مسئله‌ای گفته می‌شود که نرم‌افزار برای حل مشکلات آن ساخته می‌شود.
<!-- ==================================== -->
در پروژه ما:
دامنه اصلی: مدیریت و فروش اینترنتی کالا (Online Retail / E-commerce)
سیستم باید بتواند فرایند خرید اینترنتی را از مشاهده محصول تا ثبت سفارش و پرداخت مدیریت کند.
<!-- ==================================== -->
اهداف اصلی دامنه
مدیریت مشتریان ثبت‌نام، ورود، اطلاعات حساب و نشانی مشتری
مدیریت محصولات تعریف کالا، قیمت، دسته‌بندی و موجودی
فرایند خرید سبد خرید، ثبت سفارش و پرداخت
تحویل سفارش مدیریت وضعیت سفارش و ارسال کالا

مثال: وقتی مشتری یک گوشی را انتخاب می‌کند، وارد سبد خرید می‌شود و سفارش را ثبت می‌کند، سیستم باید قیمت کالا، موجودی، هویت مشتری و وضعیت پرداخت را به‌درستی مدیریت کند. تمام این فعالیت‌ها در دامنه فروشگاه اینترنتی قرار می‌گیرند.
<!-- ==================================== -->
زیر‌دامنه‌ها (Subdomain) :

1-  مشتری و هویت (Customer & Identity) :
ثبت‌نام و ورود با ایمیل
مدیریت حساب کاربری و نشانی‌ها
احراز هویت و کنترل دسترسی

2- کاتالوگ محصولات(Catalog) :
تعریف و ویرایش محصول
دسته‌بندی و جست‌وجوی کالا
مدیریت اطلاعات و قیمت نمایش‌داده‌شده

3- موجودی انبار(Inventory) :
ثبت تعداد موجودی هر کالا
بررسی امکان تأمین سفارش
 کاهش یا آزادسازی موجودی هنگام خرید یا لغو

4-  سبد خرید(Cart) :
افزودن و حذف کالا
تغییر تعداد کالا
محاسبه جمع موقت سبد خرید

5- سفارش‌ها(Order) : 
ثبت سفارش نهایی
نگهداری اقلام و قیمت زمان خرید
مدیریت وضعیت سفارش و لغو آن

6- پرداخت( Payment) : 
درخواست پرداخت از درگاه
ثبت نتیجه تراکنش
مدیریت پرداخت موفق، ناموفق و بازگشت وجه

در این طبقه‌بندی، زیر‌دامنه اصلی یا Core Domain بخشی است که بیشترین ارزش رقابتی کسب‌وکار را ایجاد می‌کند. برای فروشگاه ساده ما، مدیریت سفارش و فرایند خرید را هسته اصلی در نظر می‌گیریم. دسته‌بندی Core، Supporting و Generic به ماهیت واقعی کسب‌وکار بستگی دارد و برای تمام فروشگاه‌ها یکسان نیست.

| واژه | تعریف در پروژه |
|---|---|
| Customer | مشتری‌ای که حساب کاربری دارد و می‌تواند خرید کند. |
| Product | کالایی که اطلاعاتی مانند نام، شناسه و قیمت دارد. |
| SKU | شناسه یک نوع یا گونه مشخص از کالا برای مدیریت کاتالوگ و موجودی. |
| Cart | مجموعه موقت کالاهایی که مشتری برای خرید انتخاب کرده است. |
| Order | سابقه رسمی خرید که پس از ثبت نهایی ایجاد می‌شود. |
| Order Item | یک ردیف از سفارش شامل کالا، تعداد و قیمت ثبت‌شده هنگام خرید. |
| Inventory | اطلاعات موجودی قابل‌فروش کالاها. |
| Payment | فرایند و سابقه تلاش برای دریافت وجه سفارش. |
| Payment Status | وضعیت پرداخت؛ مانند Pending، Paid یا Failed. |
| Bounded Context | مرزی که درون آن مدل‌ها، قوانین و معنای واژه‌ها تعریف مشخصی دارند. |

مثال عملی از زبان مشترک : 
فرض کنیم مشتری دو عدد از یک محصول را خریداری می‌کند.

نکته مهم این است که قیمت محصول در کاتالوگ با قیمت ثبت‌شده در سفارش یک مفهوم یکسان نیست. قیمت کاتالوگ می‌تواند تغییر کند، اما سفارش باید قیمت زمان خرید را حفظ کند.

طراحی Bounded Context و ارتباط بین بخش‌ها : 

هر Bounded Context محدوده‌ای است که در آن مدل دامنه معنای مشخصی دارد. در معماری مونولیتیک، این مرزها معمولاً به‌صورت ماژول‌های جدا در یک برنامه پیاده‌سازی می‌شوند؛ نیازی نیست هرکدام سرور مستقل داشته باشند.

مرزهای پیشنهادی پروژه : 

مسئول حساب کاربری، احراز هویت و مجوز دسترسی است  .(Identity Context )
مسئول اطلاعات محصولات، دسته‌بندی‌ها و قیمت جاری است. (Catalog Context)
مسئول موجودی قابل‌فروش، رزرو موجودی و آزادسازی آن است. (Inventory Context)
مسئول انتخاب‌های موقت مشتری و محاسبه جمع سبد خرید است. (Cart Context)
مسئول ایجاد سفارش، ثبت اقلام و مدیریت چرخه عمر سفارش است. (Order Context)
مسئول تراکنش‌ها، نتیجه پرداخت و بازگشت وجه است. (Payment Context)

فرایند خرید را به‌ترتیب زیر در نظر می‌گیریم:

سیستم هویت مشتری را مشخص می‌کند و سبد خرید به حساب او مرتبط می‌شود. (Identity → Cart)

اطلاعات کالا و قیمت جاری برای نمایش به مشتری دریافت می‌شود. (Catalog → Cart)

مشتری خرید را تأیید می‌کند و سیستم درخواست ایجاد سفارش می‌دهد. (Cart → Order)

موجودی کالا بررسی و در صورت امکان برای سفارش رزرو می‌شود. (Order → Inventory)

پس از آماده شدن سفارش برای پرداخت، درخواست پرداخت ایجاد می‌شود. (Order → Payment)

نتیجه معتبر پرداخت به سفارش اعلام می‌شود تا وضعیت آن به‌روزرسانی شود. (Payment → Order)

بررسی دو ابهام یا چالش پروژه : 

چالش اول: هم‌زمانی خرید و موجودی کالا

مسئله: فرض کنیم تنها یک عدد از یک کالا موجود است، اما دو مشتری هم‌زمان برای خرید آن اقدام می‌کنند.اگر هر دو درخواست، موجودی را قبل از ثبت سفارش یک عدد ببینند، احتمال دارد هر دو سفارش ثبت شوند؛ در نتیجه فروش بیش از موجودی رخ می‌دهد.

راهکار پیشنهادی:

1.بررسی موجودی باید در سمت سرور انجام شود.

2.رزرو یا کاهش موجودی باید به‌شکل اتمیک و با کنترل هم‌زمانی در پایگاه داده صورت گیرد.

3.گر پرداخت ناموفق شد یا سفارش لغو شد، موجودی رزروشده باید طبق قوانین مشخص آزاد شود.

4.عملیات تکراری درگاه پرداخت باید با سازوکار جلوگیری از اجرای تکراری (Idempotency) مدیریت شوند.

تصمیم معماری: منطق رزرو موجودی در Inventory Context قرار می‌گیرد و Order Context از طریق یک رابط مشخص با آن ارتباط می‌گیرد.

چالش دوم: تغییر قیمت محصول پس از افزودن به سبد خرید

مسئله: مشتری محصولی را با قیمت ۱۰۰ واحد پولی به سبد خرید اضافه می‌کند؛ سپس قیمت محصول به ۱۲۰ تغییر می‌کند. هنگام ثبت سفارش کدام قیمت باید اعمال شود؟

این موضوع یک ابهام در قوانین کسب‌وکار است و باید قبل از پیاده‌سازی تعیین تکلیف شود.

راهکار پیشنهادی برای نسخه اولیه:

سبد خرید قیمت جاری را برای نمایش دریافت می‌کند.

هنگام نهایی‌کردن خرید، قیمت و موجودی در سمت سرور دوباره بررسی می‌شوند.

اگر قیمت تغییر کرده باشد، مبلغ جدید به مشتری نمایش داده می‌شود و تأیید او گرفته می‌شود.

- پس از ثبت سفارش، قیمت هر Order Item ذخیره می‌شود تا تغییرات آینده کاتالوگ، سابقه خرید را تغییر ندهند.

تصمیم معماری: Catalog Context مالک قیمت جاری است و Order Context مالک قیمت ثبت‌شده در سفارش خواهد بود.
